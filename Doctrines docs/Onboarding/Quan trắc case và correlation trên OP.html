QUAN SÁT OP (MEMBER_PROMOTE) — status & correlation_id © theo thiết kế

Hai “trục” cần tách:

Trục Ý nghĩa
onboarding_cases.status Trạng thái instance OP (DRAFT → … → APPROVED)
members.status Trạng thái thành viên (DU_BI → CHINH_THUC chỉ khi APPROVE)
correlation_id © ID theo dõi một process instance / chuỗi BPL gắn case đó

1. Mở OP (sau RP duyệt / tạo member DU_BI)

Ai: BE openMemberPromoteInstance (handoff Register → OP).

Field Giá trị
process_kind MEMBER_PROMOTE
case_type MEMBER_JOIN hoặc CLAN_SETUP
status DRAFT
correlation_id UUID mới (một C cho cả đời instance OP này)
primary_member_id member DU_BI
user_id user liên kết

BPL lúc mở (nếu có log): thường một dòng create/open với cùng C; process_type tùy implement (không đổi status case ngoài DRAFT).

Không đổi: members.status = DU_BI.

2. Lưu nháp Base Profile (PUT /members/:id)

Bảng Thay đổi
members Cập nhật field (tên, sinh, generation…)
onboarding_cases.status Giữ DRAFT
correlation_id Không đổi
BPL Có thể không ghi, hoặc log “profile save” với cùng C (nếu có)

Đây là lý do nhìn case vẫn DRAFT sau Lưu nháp — đúng.

3. Gửi duyệt (POST .../cases/:caseId/submit) — chỗ bạn vừa PASS

Field Trước Sau (kỳ vọng)
onboarding_cases.status DRAFT (hoặc NEEDS_REVISION) SUBMITTED
submitted_at null timestamp
correlation_id C₀ Vẫn C₀ (không sinh C mới)
members.status DU_BI DU_BI (chưa chính thức)

BPL kỳ vọng: 1 bản ghi process_type ≈ ONBOARDING_SUBMIT (hoặc map SRPF SUBMIT), correlation_id = C₀, payload có previous_status: DRAFT.

Nếu sau submit mà status case vẫn DRAFT → update status trong submitCase chưa chạy / nhánh OP khác nhánh bạn quan sát.
Nếu BPL không có dòng mới hoặc C khác → logger/correlation wiring lệch SSOT.

4. Admin bắt đầu review (B2 — START_REVIEW)

Field Kỳ vọng
status SUBMITTED → UNDER_REVIEW
correlation_id Cùng C₀
members.status vẫn DU_BI

BPL: ONBOARDING_REVIEW_START, cùng C.

5a. Trả về sửa (RETURN_FOR_REVISION)

Field Kỳ vọng
status → NEEDS_REVISION (+ review_note)
correlation_id Cùng C₀
Member vẫn DU_BI

User sửa → Lưu nháp (status có thể vẫn NEEDS_REVISION) → Submit lại → SUBMITTED lại, vẫn C₀.

5b. Duyệt (APPROVE)

Field Kỳ vọng
onboarding_cases.status → APPROVED (terminal)
members.status DU_BI → CHINH_THUC (side-effect definition)
correlation_id Cùng C₀ đến hết instance
User role không auto CLAN_ADMIN

BPL: ONBOARDING_APPROVE, cùng C.

5c. Từ chối (REJECT)

Field Kỳ vọng
Case → REJECTED (terminal)
Member thường vẫn DU_BI (trừ khi policy khác)
C Cùng C₀

Sơ đồ rút gọn

[Open OP]  case=DRAFT, member=DU_BI, C = C0 (mới)
    │
    ├─ Lưu nháp ──► case=DRAFT (không đổi), member fields cập nhật, C=C0
    │
    └─ Gửi duyệt ─► case=SUBMITTED, member=DU_BI, C=C0
                        │
           ┌────────────┼────────────┐
           ▼            ▼            ▼
     UNDER_REVIEW  (optional)   (một số flow gộp)
           │
     ┌─────┴─────┐
     ▼           ▼
NEEDS_REVISION  APPROVED / REJECTED
     │              │
  Submit lại    member=CHINH_THUC (chỉ APPROVED)
  → SUBMITTED       C vẫn = C0

correlation_id — nguyên tắc

Sự kiện C
Tạo instance OP Sinh C mới
Mọi action trên cùng case (save, submit, review, approve) Giữ nguyên C
OP mới (member khác / instance khác) C khác
RP (REGISTER) trước đó C của RP — không trộn với C OP (metadata có thể trỏ source_register_correlation_id)

Vì sao quan sát “status / BPL không đổi đúng”

Thường gặp:

  1. Lưu nháp không đụng onboarding_cases.status → nhìn case vẫn DRAFT (đúng).
  2. Submit đã 200 nhưng UI/DB bạn xem replica / cache / case id khác.
  3. BPL ghi correlationId từ request header khác cases.correlation_id → trông như “C nhảy”.
  4. Submit nhánh legacy vs SRPF không cùng chỗ update status + BPL.

Kiểm tra 1 case cụ thể (SQL ý tưởng):

-- case
SELECT id, status, process_kind, correlation_id, submitted_at, updated_at
FROM onboarding_cases
WHERE id = '<caseId>';

-- BPL cùng C
SELECT id, process_type, correlation_id, created_at, payload
FROM business_process  -- tên bảng đúng schema của bạn
WHERE correlation_id = '<correlation_id của case>'
ORDER BY created_at;

Sau Gửi duyệt thành công: case phải SUBMITTED, submitted_at not null, BPL thêm 1 dòng SUBMIT cùng correlation_id.

Nếu bạn paste 1 hàng onboarding_cases (status, process_kind, correlation_id, submitted_at) trước/sau Gửi duyệt + vài dòng BPL cùng C, có thể chỉ đúng chỗ lệch (status không update vs BPL sai C).
